# Proposed update to Mozilla 1788206 — not posted

I reproduced the transfer cost with a small, public WebGL probe on macOS and
Linux, including release Firefox 159.0.1 and Linux Nightly 162.0a1
(build 20261106044122). The probe records draw, transfer-to-bitmap and
transfer-from-bitmap separately, varies 512/1024/2048 square surfaces and alpha,
and keeps untimed pixel verification separate.

The bitmap-creation stage dominates the synchronous cost and grows with surface
area. The latest Nightly still shows the issue. Chromium is a useful control;
these are API timings, not proof of display throughput or zero GPU work.
At 2048 square, native Mac Firefox 159.0.1 measured creation medians of
10.14/10.56 ms (alpha/opaque), and Linux Nightly 162.0a1 measured 9.84/12.04 ms.
Those vendor probes have one context, 10 warmups and 100 calls per case.
The direct probe's late source snapshots use `preserveDrawingBuffer=false`;
blank readbacks there are not treated as display defects. The timing table
does not compare version regressions across differing graphics environments.

Reproduction: [probe and method](https://github.com/cdeil/flutter-wasm-check/blob/main/docs/measurements-2026-11-06.md).
The raw data includes GL renderer strings and the Linux display configuration;
privacy-masked renderer aliases are not treated as exact hardware identities.

Would an image/texture lifetime test or a worker-transfer extension to this
probe be useful for the GPU-backed ImageBitmap path described in comment 38?
The video fast-path bugs linked there are already fixed; this is a canvas-only
case. I have not built or validated a Firefox C++ fix.
